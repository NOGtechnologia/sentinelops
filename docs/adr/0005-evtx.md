# ADR-0005: EVTX-Verarbeitung und -Erzeugung

## Kontext

EVTX ist ein binäres, undokumentiert-proprietäres Format (Chunk-basiert, Binary XML). Für den
Import wird eine Bibliothek gebraucht; der Generator muss Windows-Ereignisse erzeugen.

## Messung (Phase 0, reproduzierbar mit `scripts/bench_evtx.py`)

Datei `backend/tests/fixtures/evtx/security.evtx` (2.261 Datensätze), Windows Server 2022,
Python 3.12:

| Bibliothek | Ausgabe | Zeit | Datensätze/s |
|---|---|---:|---:|
| `evtx` 0.13.1 (Rust, `omerbenamram/evtx`) | JSON | 0,015 s | ≈ 150.000 |
| `evtx` 0.13.1 | XML | 0,017 s | ≈ 135.000 |
| `python-evtx` (reines Python) | XML | 8,7 s | ≈ 260 |

Zusätzlich: `python-evtx` und `evtx` kollidieren im Python-Namensraum (`Evtx`/`evtx` auf
Windows ohne Groß-/Kleinschreibung) und können nicht gemeinsam installiert werden.

## Entscheidung

- Import mit **`evtx` (MIT)** und JSON-Ausgabe; die JSON-Darstellung eines Datensatzes wird als
  Rohsatz gespeichert und vom selben Code wie Windows-JSON gemappt (identische Normalisierung).
- Defekte Datensätze landen in der Quarantäne; nach 1.000 aufeinanderfolgenden Fehlern wird die
  Datei abgebrochen.
- Der **Generator erzeugt kein EVTX**, sondern Windows-Event-XML und Winlogbeat-/Get-WinEvent-JSON.
  Ein EVTX-Schreiber existiert nicht als gepflegte Bibliothek; die EVTX-Parser-Pfade werden mit
  echten Beispieldateien aus `omerbenamram/evtx` (MIT) getestet.

## Konsequenzen

Rust-Wheel-Abhängigkeit (verfügbar für Linux/macOS/Windows, x86_64/arm64). Der Benchmark ist im
Repository und kann bei Bibliotheksupdates wiederholt werden.
